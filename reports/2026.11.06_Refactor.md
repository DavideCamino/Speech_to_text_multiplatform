## 1. Unused code

 Scope and verification: I inspected the first-party Rust source, unit and integration tests, examples, packaging scripts, and CI
 workflows, and traced symbol references across them. I reviewed the vendored dependency’s patch documentation, but did not audit
 the entire upstream Whisper/GGML implementation.

 No files were changed. Git status was clean before and after inspection. This was a static review; I did not run builds or tests,
 which would create or update artifacts.

 ### U1. Unused Markdown parser bookkeeping — confirmed

 Location: src/ui/markdown_buffer.rs:101–144

 The parser computes tag.to_end() and stores the resulting TagEnd in each entry of the open stack:

 ```rust
   open.push((end, style.map(|style| (style, doc.length))));
 ```

 When an entry is removed, that stored value is explicitly ignored:

 ```rust
   if let Some((_, Some((style, start)))) = open.pop()
 ```

 The stored end tag does not contribute to rendering or validation.

 Recommendation: Remove the unused tuple component, retaining the stack’s optional style/start entries. Alternatively, use it for
 nesting validation if that is an intentional requirement. Do not remove unstyled stack entries: they still preserve nesting.

 Priority: Low; straightforward cleanup.

 ### U2. Unused return value from packaging helper — confirmed

 Location: build-aux/windows/package.py:89

 copy_tree() returns a Boolean indicating whether a directory was copied. All current calls ignore that result:

 - Line 150: runtime resource directories.
 - Line 152: icon themes.
 - Line 155: schemas.
 - Line 196: license directories.

 The function itself is used; its return-value contract is not.

 Recommendation: Return None, preserving the distinction between optional missing directories and required-directory errors.

 Priority: Low.

 ### U3. No confirmed abandoned first-party modules or unused direct dependencies

 I did not find a justified whole-module or direct-dependency removal candidate.

 Important cases that should not be misclassified as unused:

 - Transcript::text() is used by tests and examples/transcribe.rs, even though the GUI uses its editable text buffer.
 - GTK test helpers without #[test] are explicitly invoked from the single GTK test entry point in src/ui/tests.rs.
 - GPU variants are used by persisted settings, feature-gated builds, and tests; absence from a CPU build does not make them
   obsolete.
 - build-aux/flatpak/install-licenses.py is also used by Windows packaging.
 - vendor/whisper-rs-sys is selected by [patch.crates-io] in Cargo.toml; it is not an unused vendor copy.
 - Cancellation-on-drop implementations perform essential cleanup even without explicit method calls.

 Conclusion: The useful cleanup is mostly removal of unnecessary bookkeeping and simplification of active code—not large-scale
 deletion.

## 2. Redundant code

 ### R1. Repeated one-shot background-worker polling

 Locations:

 - src/ui/mod.rs:591 — model availability.
 - src/ui/mod.rs:1056 — download destination checking.
 - src/ui/mod.rs:1166 onward — device discovery and model scanning.
 - Startup preferences loading uses a similar pattern.

 Each repeats the same structure:

 1. Inspect an optional receiver.
 2. Call try_recv().
 3. Treat Empty as pending.
 4. Convert disconnection into a fallback or error.
 5. Remove the receiver after completion.
 6. Update widgets and refresh controls.

 Why it matters: The plumbing obscures the operation-specific behavior and creates multiple places to maintain channel-lifecycle
 handling.

 Recommendation: Introduce a small helper for one-shot tasks, allowing each caller to supply its own disconnected-worker result.
 Keep streaming jobs separate.

 Priority: Medium.

 ### R2. Existing background helper is not used consistently

 Locations:

 - src/ui/mod.rs:59 — background().
 - src/ui/mod.rs:67 — discover_devices().
 - src/ui/mod.rs:926 — refresh_models().

 discover_devices() simply forwards its closure to background(). Conversely, refresh_models() manually recreates the
 channel/thread/send sequence already implemented by background().

 Recommendation:

 - Use background() for model scans.
 - Either remove the forwarding-only discovery wrapper or give it an actual domain-specific responsibility.
 - Preserve the background-thread discovery test.

 Priority: Low.

 ### R3. Two Markdown-to-text interpretations

 Locations:

 - src/ui/markdown_buffer.rs:90 — display parser.
 - src/ui/rewrite.rs:12 — TXT export parser.

 Both interpret Markdown events, but they already differ:

 ┌───────────────┬─────────────────────────────────────────┬───────────────────────┐
 │ Feature       │ Display                                 │ TXT export            │
 ├───────────────┼─────────────────────────────────────────┼───────────────────────┤
 │ Strikethrough │ Enabled and styled                      │ Extension not enabled │
 ├───────────────┼─────────────────────────────────────────┼───────────────────────┤
 │ Task lists    │ Enabled, rendered with checkbox symbols │ Extension not enabled │
 ├───────────────┼─────────────────────────────────────────┼───────────────────────┤
 │ List markers  │ Generated                               │ Not generated         │
 ├───────────────┼─────────────────────────────────────────┼───────────────────────┤
 │ HTML          │ Displayed literally                     │ HTML events ignored   │
 ├───────────────┼─────────────────────────────────────────┼───────────────────────┤
 │ Block spacing │ Richer layout rules                     │ Simpler newline rules │
 └───────────────┴─────────────────────────────────────────┴───────────────────────┘

 This is not necessarily incorrect—display and plain-text export can intentionally differ—but the differences are currently embedded
 in two implementations rather than expressed as a clear policy.

 Recommendation: Share Markdown options and parsing semantics, then make display/export differences explicit. Add tests defining the
 intended TXT output before consolidating anything.

 Priority: High for consistency and maintainability.

 ### R4. Application construction is duplicated in tests

 Locations:

 - src/ui/mod.rs:153 — build_loaded().
 - src/ui/tests.rs:456 — test_app().

 Both initialize the large App structure field by field. The test version substitutes an in-memory save operation and omits some
 production wiring.

 Why it matters: Every new field needs matching edits in two constructors. Tests can unintentionally exercise an initialization path
 that differs from production.

 Recommendation: Extract a shared constructor that accepts settings and a save-worker dependency. Keep window presentation, timer
 installation, and external discovery outside it.

 Priority: Medium.

 ### R5. Model-selection presentation and update logic is repeated

 Locations:

 - src/ui/preferences.rs:256 — initial model filename label.
 - src/ui/mod.rs:641 — model label refresh.
 - src/ui/mod.rs:949 — selecting an existing model.
 - src/ui/mod.rs, download completion handling — selecting an imported/downloaded model.

 The same filename/fallback formatting is implemented twice. Selection changes also repeat the sequence of assigning settings,
 persisting, and updating model availability/presentation.

 Recommendation: Centralize the model presentation and accepted-selection update. Keep caller-specific actions—closing the model
 window or refreshing its list—outside that shared operation.

 Priority: Low to medium.

 ### R6. Repeated cancellation-aware network waiting

 Locations:

 - src/model.rs:135 — cancellable().
 - src/llm/client.rs:12 — interruptible().

 Both pin a future and periodically check an atomic cancellation flag while awaiting it.

 Their policies differ:

 - Different polling intervals.
 - Different error types/messages.
 - LLM operations have an additional 120-second timeout.
 - Model downloads have request/client timeout settings.

 Recommendation: Consider sharing only the cancellation-wait mechanism, with explicit timeout and error policies. Do not merge the
 HTTP clients: their redirect/proxy behavior and privacy requirements differ.

 Priority: Low; worthwhile only if the extracted helper remains easier to read.

 ### R7. Unnecessary ownership scaffolding in export saving

 Location: src/ui/dialogs.rs:94–98

 Inside the file-dialog completion callback:

 - content is cloned before being converted to bytes.
 - done is wrapped in an Rc, but that Rc is never cloned.

 These callbacks are one-shot, so the owned content and completion callback can be moved into the asynchronous write callback.

 Recommendation: Remove the unnecessary clone and reference-counted wrapper.

 This does not apply to the export snapshot in src/ui/mod.rs:856 onward: that snapshot protects against an old save incorrectly
 marking newer edits as saved.

 Priority: Low.

 ### R8. Repeated audio-window constants and calculations

 Location: src/transcription/worker.rs:122 and :272

 File and microphone processing independently specify the 28-second inference window and repeat sample-count-to-millisecond
 calculations and overlap conversion.

 Recommendation: Share named constants and small time-conversion helpers. Keep file and microphone orchestration separate: EOF
 lookahead, live inference cadence, Stop acknowledgement, and resampler flushing are genuinely different.

 Priority: Medium.

 ### R9. Duplicated WAV fixture construction

 Locations:

 - tests/backend.rs:8 — wav().
 - src/transcription/worker.rs:444 — silence().

 Both manually write a PCM WAV header. Their audio payloads differ, but the container-writing code is substantially the same.

 Recommendation: Share a test-only WAV writer if it can be introduced without exposing test infrastructure through the production
 API. Keep fixture parameters and assertions local.

 Priority: Low.

## 3. Refactoring

 Overall assessment: An incremental refactor is justified, but a rewrite is not. The backend already has useful boundaries around
 capture, decoding, resampling, inference, overlap reconciliation, and LLM streaming. The largest readability problem is the UI
 controller and its dispersed state management.

 ### Phase 1 — Apply small, behavior-preserving cleanups

 Address U1, U2, R2, R5, and R7 first.

 Also:

 - Replace small unnecessary rebinding, such as let mut response = response in src/llm/client.rs:80, with a mutable initial binding.
 - Give repeated window sizes and timing values meaningful names.
 - Correct “Sistem Prompt” in UI strings and corresponding tests.
 - Update examples/download_model.rs help text: its catalog lookup also accepts models beyond the advertised tiny/base/small
   choices.

 Expected result: Less incidental code with minimal architectural risk.

 ### Phase 2 — Split the UI controller by responsibility

 Primary target: src/ui/mod.rs — 1,372 lines.

 The file currently combines:

 - Startup and window construction.
 - Signal/action wiring.
 - Settings persistence and shutdown.
 - Model selection, scanning, importing, and downloading.
 - Device discovery.
 - Transcription lifecycle.
 - Export tracking.
 - Rewrite navigation.
 - All major polling and sensitivity rules.

 A practical initial split:

 ```text
   src/ui/
     mod.rs                    # Public entry point and composition
     app.rs                    # App structure and shared construction
     actions.rs                # Signals, menu actions, shortcuts
     lifecycle.rs              # Preferences persistence and closing
     model_controller.rs       # Model scans, selection, imports/downloads
     transcription_controller.rs
     export.rs
     rewrite.rs                # Existing rewrite controller
     task.rs                   # Small one-shot worker helpers
 ```

 Initially, these can remain separate impl App blocks. There is no need to introduce a framework or a large trait hierarchy.

 Also split these long methods:

 - connect() into feature-specific connection methods.
 - poll() into device/model/transcription/download polling methods.
 - refresh() into focused control-update methods.

 Expected result: Each workflow can be understood without reading the entire controller.

 ### Phase 3 — Make state ownership and transitions explicit

 Targets: App in src/ui/mod.rs and rewrite state in src/ui/rewrite.rs.

 Several related states are spread across separate fields:

 - Transcript, provisional text, renderer, and dirty flags.
 - Transcription job and recording flag.
 - Closing and allow-close flags.
 - Model scan/check/download state.

 Group these by responsibility, and use enums where they clarify mutually exclusive states—for example:

 - Window lifecycle: open, saving-before-close, ready-to-close.
 - Transcription session: idle or running with source/job metadata.

 Avoid putting all work into one global “busy” enum: some operations legitimately coexist.

 Important distinctions to preserve:

 - Edited transcript text and original subtitle segments are different data.
 - dirty and text_dirty encode different export behavior.
 - Stop finishes buffered recording; Cancel discards unfinished inference.
 - Saving an older snapshot must not clear newer changes.
 - Dropping a job must still cancel it.

 Centralize sensitivity updates so callbacks do not compete with refresh() to define the same widget state. Preserve explicit
 transitional states such as “cancelling.”

 Expected result: Fewer implicit invariants and clearer state transitions.

 ### Phase 4 — Separate Markdown parsing from GTK rendering

 Target: src/ui/markdown_buffer.rs.

 Its production code combines pure parsing, text-diff calculation, tag management, selection preservation, and viewport-follow
 logic.

 Split it into:

 1. A GTK-independent Markdown document representation.
 2. Explicit plain-text export policy.
 3. GTK buffer application.
 4. Scroll-follow/anchor handling.

 Remove the unused end-tag bookkeeping during this work.

 Do not replace the existing incremental buffer updates with whole-buffer replacement: current tests deliberately protect selection,
 scrolling, and stable-prefix behavior.

 Expected result: Smaller units with pure parsing tests that do not require GTK.

 ### Phase 5 — Improve test organization without losing GTK safety

 Target: src/ui/tests.rs — 1,236 lines.

 Organize helpers by feature:

 ```text
   src/ui/tests/
     mod.rs
     support.rs
     transcription.rs
     models.rs
     preferences.rs
     rewrite.rs
     lifecycle.rs
 ```

 Preserve the single GTK-thread entry point. Turning every helper into an independent parallel #[test] would violate the
 initialization constraint documented in the current suite.

 Move generic GTK waiting helpers out of markdown_buffer.rs into shared test support, and use the shared App constructor from Phase
 2.

 Add focused regression coverage for:

 - One-shot worker disconnection and stale results.
 - Consistent Markdown export semantics.
 - Shutdown and save-failure transitions.
 - Cancellation and control re-enabling.

 Expected result: Easier test navigation and less duplicated setup.

 ### Phase 6 — Clarify packaging structure

 Targets:

 - build-aux/windows/package.py:105 — assemble().
 - build-aux/flatpak/install-licenses.py.

 Split assemble() into named stages: validation, runtime copying, dependency collection, license collection, metadata generation,
 and archive creation.

 Move the cross-platform license installer into a shared packaging location rather than keeping Windows dependent on a helper under
 flatpak/. Update both packaging paths and their tests together.

 Keep platform-specific packaging separate; the current Windows and Flatpak differences are substantive.

 Expected result: A readable packaging pipeline with clearer shared ownership.

 ### Validation plan

 For implementation of this plan:

 1. Run formatting and Clippy for all targets.
 2. Run Rust tests for CPU and Vulkan configurations.
 3. Run GTK tests under the existing virtual-display/session-bus setup.
 4. Run both Python packaging test suites.
 5. Verify Windows portable and installer smoke tests on Windows.
 6. Manually verify recording Stop/Cancel, append after editing, model replacement, export snapshots, streamed Markdown scrolling,
    and close/save failure behavior.
 7. Check other GPU feature builds on appropriate toolchains before declaring cross-platform equivalence.

 Recommended order: Small cleanups → shared construction and UI file split → worker polling → state organization → Markdown
 separation → packaging cleanup.

 Bottom line: There is little clearly unused code. The greatest improvement will come from making active code easier to navigate,
 centralizing repeated lifecycle logic, and documenting intentional differences—not aggressively deleting defensive checks or
 merging workflows that behave differently.
